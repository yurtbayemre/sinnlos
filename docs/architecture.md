## 1. Überblick & Topologie

Sinnlos ist ein Firmen-Intranet als pnpm-Monorepo mit zwei Apps: `apps/web` (Next.js 16, fast rein serverseitig, App Router + RSC) und `apps/cms` (Strapi 5, Node 24, Postgres in Prod / SQLite standalone). Das Web-Frontend ist ein dünner, session-behafteter Layer vor Strapi: alle Pages sind async Server Components, die über einen zentralen `strapi()`-Fetch-Client (`apps/web/src/lib/strapi.ts`) mit dem Strapi-JWT der Auth.js-Session lesen; Mutationen laufen ausschließlich über Server Actions in `apps/web/src/lib/*-actions.ts`. Autorisierung liegt konzeptionell im CMS (Rollen-Bootstrap + Route-Policies); das Web-Layer prüft Rollen nur für UI-Gates (`isAdmin`). Auth: Microsoft Entra ID (OAuth → Token-Exchange gegen Strapi-JWT) und/oder lokale Credentials, beides env-geschaltet; ein `DEMO_MODE=1` ersetzt Strapi komplett durch In-Memory-Fixtures (`lib/demo.ts`).

Deployment: 4-Container-Stack via `docker compose -p infra` (`infra/docker-compose.yml`): `db` (postgres:16-alpine) → `cms` (Strapi :1337) → `web` (Next standalone :3000) → optional `caddy`. In Prod (VPS, `sinnlos.yurtbay.dev`) deaktiviert `infra/docker-compose.traefik.yml` den Caddy (`profiles: [manual]`) und hängt web+cms per Labels an den Host-Traefik (externes Netz `frontend`, TLS via `lehttp`). Das Pfad-Routing ist die zentrale Topologie-Invariante — **Router-Prioritäten: `/api/auth/*` → web (Prio 100), `/api|/admin|/upload|…` → cms (Prio 50), Catch-all → web (Prio 1)** — und existiert doppelt (Traefik-Labels + `infra/Caddyfile`); die Doppelpflege ist seit [#22](https://github.com/yurtbayemre/sinnlos/issues/22) durch `infra/routing-parity.test.ts` abgesichert (Prefix-Mengen + Verhaltens-Proben unter den ECHTEN Matcher-Semantiken beider Proxies). **`/uploads` (Datei-Bytes) geht seit [#21](https://github.com/yurtbayemre/sinnlos/issues/21) bewusst NICHT mehr zu Strapi**, sondern an den Web-Catch-all → session-gegatete Proxy-Route `apps/web/src/app/uploads/[...path]/route.ts` (s. §7b P1.4). **Matcher-Landmine dabei:** Traefiks `PathPrefix` matcht als ROHER String-Präfix (an Traefik 3.7 live verifiziert: `/email` matcht `/emailXYZ`) — `PathPrefix(\`/upload\`)` würde `/uploads` weiter schlucken, daher steht die Media-Library-Admin-API segment-exakt als ``Path(`/upload`) || PathPrefix(`/upload/`)`` in den Labels (Caddy-Pendant: `/upload /upload/*`). Konsequenzen im Code: Next-eigene Endpunkte dürfen nicht unter `/api/*` liegen (ICS-Route lebt unter `/events/[id]/ics`), `/admin` ist für Strapi reserviert, und der Revalidate-Webhook (`/api/revalidate`) ist von außen unerreichbar, weil Traefik `/api` zu Strapi routet — CMS ruft ihn intern über `WEB_INTERNAL_URL` auf.

```
Browser ──HTTPS──> Traefik (frontend-Netz)
                     ├─ /api/auth/* ────────────> web:3000  (Auth.js)
                     ├─ /api|/admin|/upload|… ──> cms:1337  (Strapi; NICHT /uploads)
                     └─ /* (inkl. /uploads) ────> web:3000  (Next RSC; /uploads = Session-Gate-Proxy)
web ──Bearer strapiJwt──> cms ──> db (postgres, kein Host-Port)
web ──GET /uploads/* (intern, STRAPI_URL)──> cms (Datei-Bytes für die Session-Route)
cms ──POST /api/revalidate (x-revalidate-secret)──> web (intern, WEB_INTERNAL_URL)
```

## 3. Request-/Datenfluss

**Auth-Kette:**
1. Route-Guard: `apps/web/src/proxy.ts` (Next-16-„proxy", Nachfolger von middleware.ts) prüft pro Request die Auth.js-Session, redirectet unauth → `/sign-in?from=…`. Public-Allowlist (`proxy.ts:37-49`): `/sign-in`, **`/register` (jetzt drin, Redirect-Kreis behoben)**, `/api/auth`, `/api/revalidate`, `/_next`, `/favicon` + exakte PUBLIC_FILES. `DEMO_MODE=1` schaltet alles ab (Prod-Guard in `auth.ts:24-28` wirft dann beim Start).
2. Login Microsoft: Entra-OAuth → `auth.ts:64-102` tauscht das Access-Token gegen einen Strapi-JWT via `/api/auth/microsoft/callback` (3 Versuche, Backoff 0/500/1500ms, 5s-Timeout, Retry nur bei 5xx). CMS-seitig (`extensions/users-permissions/strapi-server.ts:74-162`): Graph-Enrichment (/me, /memberOf, /manager), **Rollen-Remap bei jedem Login** via `config/ms-role-map.ts` (first-match-wins, Fallback `member`), Department-Match per Name, Manager via `microsoftOid`. Scope enthält jetzt `GroupMember.Read.All` (`config/plugins.ts:39`) — Gruppen-Mapping funktioniert (braucht Tenant-Admin-Consent).
3. Login lokal: Credentials-Provider → Strapi `/api/auth/local`, dann Nachladen von `/api/users/me?populate=role,department` (`auth.ts:126-168`).
4. Session: JWT-Strategie, `maxAge` 7d **exakt = Strapi-JWT-TTL** (`auth.ts:175` ↔ `apps/cms/config/plugins.ts`). Session trägt `strapiJwt`, `provider`, `user.id` (number), `role`, `department`.
5. Jeder Server-Fetch: `strapi()` injiziert `Authorization: Bearer <strapiJwt>`; Autorisierung entscheidet Strapi (Matrix grob + Route-Policies fein). **NEU: 401-Handling** — abgelaufener/rotierter JWT → `redirect("/sign-in?expired=1")` statt kryptischer Fehler (`strapi.ts:65-67`).

**Caching (zweigleisig, Grundregel in `strapi.ts:24-30`):**
- Getaggte Collections (departments, teams, polls, **events — jetzt zeitfensterbasiert statt einer globalen Liste**: `api.events.upcoming/past/window`, gemeinsamer Tag `events` + 60s; Caller übergeben lokale Start-of-Day-ISO-Stamps, damit der Cache-Key max. 1×/Tag wechselt).
- Alles Nutzer-Variable strikt `noCache: true` — der Next-Fetch-Cache keyed nur per URL und ignoriert den Authorization-Header: wiki, people, announcements (inkl. `requiringAck`), kudos, notifications, poll-results, **acknowledgements, quick-links, classifieds, event-rsvps, celebrations** (alle neuen Endpoints korrekt noCache). `documents` wurde am 2026-08-15 nachgezogen (war als einzige per-User-gefilterte Collection noch getaggt — Commit c3af366).
- Invalidierung: Strapi-`after*`-Lifecycles → `utils/revalidate.ts` (fire-and-forget, 3s-Timeout, Shared Secret) → `POST WEB_INTERNAL_URL/api/revalidate` → `revalidateTag(tag, "default")` (`route.ts:37`). Tag-Schema: `<typ>s` + `<typ>:<slug>`.
- Mutierende Server Actions: `refresh()` aus `next/cache`. Kommentare/Notifications pollen client-seitig (10s/30s, nur bei sichtbarem Tab).
- Paginierte Sammel-Fetches laufen als bounded Page-Walk (Strapi-REST maxLimit 100): Acks max 20 Seiten (`lib/acknowledgements.ts`), RSVPs max 30 Seiten (`strapi.ts` `events.rsvps`).

**Fehler-Strategie:** Listen-Seiten nutzen `tryFetch()` (`lib/safe-fetch.ts`, rethrowt NEXT_REDIRECT via `unstable_rethrow`) → Inline-`FetchErrorBanner`; Detail-Seiten mit `notFound()`-Semantik lassen Fetch-Fehler bewusst zur `(app)/error.tsx` propagieren.

## 5. Konventionen & Patterns (beim Ändern zwingend kennen)

1. **Reverse-Proxy-Vertrag:** Neue Next-Endpunkte NIE unter `/api/*` (geht zu Strapi) außer `/api/auth/*`; `/admin` ist Strapi. Routing-Änderungen immer doppelt: Traefik-Labels (`infra/docker-compose.traefik.yml`) **und** `infra/Caddyfile`.
2. **Guard = `src/proxy.ts`, nicht middleware.ts** (Next 16). Neue öffentliche Routen müssen in die `isPublic`-Liste (`proxy.ts:37-49`; `/register` ist inzwischen drin).
3. **Server/Client-Split:** Pages sind ausnahmslos async RSC; Interaktivität nur in `src/components`. Über die RSC-Grenze nur serialisierbare Props — Icons als String via ICONS-Map.
4. **Mutationen = Server Actions** in `lib/*-actions.ts`; Formular-Signatur `(_prev, formData) → {error?/success?}` mit `useActionState`; Fehler-Rückgaben als Machine-Codes, Übersetzung im Form (i18n-Regel, Muster `classified-actions.ts`). Datei-Uploads laufen als FormData durch die Action (Browser hält nie den Strapi-JWT).
5. **`strapi()`-Client (`lib/strapi.ts:33-77`):** DEMO_MODE-Kurzschluss, JWT-Injektion, 401 → `redirect("/sign-in?expired=1")` (Z.65-67), `!res.ok` → throw, 204-Toleranz. Cache-Regel: per-User-Daten IMMER `noCache: true`. Neue getaggte Endpoints nur, wenn die Collection garantiert von KEINER Policy per-User gefiltert wird — und beim Aktivieren einer Policy den Cache mitziehen (Lehrfall: documents, §7 P1.1).
6. **documentId-Regel (numerische Web-ids):** Web arbeitet mit numerischen ids + Filter-Queries. Wo Strapi-v5-Core-Routen documentId erwarten, übersetzt der CMS-Controller (`comment.ts:30-32`; gleiches Muster in `classified.ts` update/delete — untranslated numeric id würde 404/204-ins-Leere).
7. **Live-Wrapper-Muster** (kein SWR/React-Query): Server-Entry lädt initial, Client-Wrapper pollt per `setInterval` nur bei `visibilityState==='visible'`; Mutations-Kinder rufen Action, dann `onChanged?.()`.
8. **CMS-Authz zweistufig:** users-permissions-Matrix (`src/index.ts:101-298`) + Route-Policies (`src/policies/`, 15 Stück). Neue Content-Types brauchen Matrix-Eintrag UND Policy-Verdrahtung im Router UND ggf. `CUSTOM_ACTION_GRANTS`-Zeile (Custom-Routen 403en sonst für alle).
9. **Lifecycles:** `relationId()`-Normalisierung vor DB-where; Notification-Fan-out per-row `create()` — NIE `createMany()` (attachRelations wird übersprungen, recipient bliebe null; belegt in `announcement/lifecycles.ts:63-69`).
10. **Rollen:** `isAdmin()` fail-closed, exakt `"admin_role"`. MS-Login remappt die Rolle bei JEDEM Login.
11. **i18n:** Cookie-basiert ohne Locale-Routing (en/de); Auth-Seiten `force-dynamic` (Runtime-Env nicht ins Image backen).
12. **URLs:** `STRAPI_URL` (intern) vs. `STRAPI_PUBLIC_URL` (Browser/Media); Client-Bundle bleibt relativ.
13. **Loading-UX:** jede Route hat `loading.tsx` + Skeleton; `PageFade` remountet per `key={pathname}`.

**NEU (Pflicht-Muster seit den Security-Runden + Modulen vom 2026-08-15):**

Immer `getMutableQuery(policyContext)` (mutiert `policyContext.request.query` in place) und den eigenen Filter per `$and` mit dem Client-Filter verknüpfen (narrow-only, nie widen). So machen es alle 7 Visibility-Policies (acknowledgement/announcement/notification/poll-vote/quick-link/wiki/document).
15. **`restrictiveIdFilter` — die sanitize-fail-open-Falle** (`policy-query.ts:62-64`): id-basierte Policies injizieren `{id:{$in:[...]}}`; bei LEERER Liste würde `sanitizeQuery` das leere Array-Operand strippen → `{id:{}}` = kein Constraint = wer NICHTS sehen darf, sähe ALLES. Deshalb Skalar-Fallback `{id:{$eq:-1}}`. Beides gegen die installierte @strapi/utils 5.49 per Repro verifiziert und in `utils/policy-query.test.ts` getestet. Verwendet von `wiki-visibility.ts:100`, `document-visibility.ts:89`, `quick-link-visibility.ts:81`, `announcement-visibility.ts:93`.
16. **id-Berechnung server-seitig statt Relations-Filter** (`utils/visible-ids.ts`): REST-Filter, die Relationen traversieren, 400en für Rollen ohne `<target>.find`-Scope (`throwRestrictedRelations`). Sichtbare Primärschlüssel daher via `strapi.db.query` (umgeht Permission-Gating) in JS bestimmen, dann nur den nicht-relationalen id-Filter injizieren.
17. **documentId-Anker für Referenzen auf draftAndPublish-Types:** Strapi 5 published per delete+recreate — die numerische id einer published Row wechselt bei JEDEM Publish. Referenzen auf announcement/event daher als `targetDocumentId`-String: `acknowledgement/controllers/acknowledgement.ts:9-15`, `event-rsvp/controllers/event-rsvp.ts:10-15`; Web matcht ebenso per documentId (`dashboard/ack-banner.tsx`). Beide Controller prüfen das Ziel als published + Feature-Flag (requiresAck bzw. rsvpEnabled) mit EINEM identischen Fehler für alle Fail-Modes (kein Existenz-Orakel für Draft-documentIds). **Seit [#11](https://github.com/yurtbayemre/sinnlos/issues/11) gilt das auch für comment/reaction** (`utils/comment-target.ts` + Web-Spiegel `lib/comment-target.ts`, Bestandsdaten per Bootstrap-Backfill migriert, s. §5.27).
18. **Write-Policy-Lookups akzeptieren id UND documentId:** `/^\d+$/`-Weiche in allen Ownership-Policies (`can-edit-wiki.ts:22`, `is-department-head.ts:21`, `is-team-member-or-lead.ts:19`, `is-classified-author.ts:18`, `is-event-rsvp-owner.ts:19`, `is-notification-recipient.ts`, `is-reaction-author.ts`) — v5-Routen tragen documentId, das Web schickt numerische ids.
19. **Upload-Härtung** (`extensions/upload/strapi-server.ts`): Content-API `POST /api/upload` ist gewrappt — (a) create-only, `?id=`-Replace verboten (Z.83-85; mit nur upload-Grant könnte man sonst JEDE Media-Datei überschreiben), (b) max 4 Dateien/Request, (c) 5MB/Datei mit fs.stat-Fallback, (d) **Magic-Byte-Allowlist JPEG/PNG/WebP** (Z.47-68, kein SVG/XSS, kein GIF; client-mimetype wird auf den gesnifften Wert normalisiert), (e) `provider_metadata.uploadedBy` = Caller-id auf jede erzeugte Datei (Z.144-161). Der classified-Controller akzeptiert nur Bild-ids mit eigenem uploadedBy (`classified.ts:74-103`, admin/editor-Bypass) — fremde Media-ids (Avatare, Dokumente) sind nicht anhängbar. Upload-Grant: 5 Rollen, nie guest/authenticated; kein find/destroy auf der Media-Library von außen.

22. **`REVOKED_PERMISSIONS`** (`index.ts:377-396`): Der Bootstrap-Sync fügt Grants nur HINZU — einen Matrix-Eintrag löschen entzieht auf einer Bestands-DB nichts. Obsolete (Rolle→Action)-Paare müssen explizit in REVOKED_PERMISSIONS, sonst bleiben sie live (so wurden guest-Kudos/-Classified/-Ack-Grants zurückgenommen).
23. **Wiki-Revision-Kontext** (`utils/wiki-edit-context.ts` + `wiki-page/controllers/wiki-page.ts:23`): Controller wrappt das Core-Update in `wikiEditContext.run({editorId, revisionSummary}, …)` (AsyncLocalStorage); der beforeUpdate-Lifecycle liest Editor/Summary via `getStore()` — Lifecycles haben kein ctx.state.
24. **`forcePublishedStatus` — die `?status=draft`-Falle** (`policy-query.ts:105-108`): Der id-Filter aus §5.15/16 kommt aus `strapi.db.query` und umfasst Draft- UND Published-Rows — WELCHE davon zurückkommen, entscheidet allein der **client-gesteuerte** `status`-Param. Der überlebt alles: `validateQuery` lässt ihn zu (`status` steht in `ALLOWED_QUERY_PARAM_KEYS`, @strapi/utils 5.49 `content-api-constants.js`), `sanitizeQuery` fasst nur `filters/sort/fields/populate` an und reicht ihn unverändert durch, und der Core-Service merged ihn ÜBER seinen eigenen Default (`getFetchParams` = `{status:'published', ...params}`, @strapi/core 5.49 `core-api/service/core-service.js`) → `status:'draft'` wird zu `lookup.publishedAt {$null:true}`. Jede Rolle mit `<type>.find` konnte damit per `?status=draft` unveröffentlichte Entwürfe lesen (per node-Repro gegen 5.49 verifiziert: validateQuery ACCEPTED, sanitizeQuery gibt den Param wörtlich zurück). Deshalb setzen **alle Read-Policies auf draftAndPublish-Types** den Param nach dem admin/editor-Bypass server-seitig: `announcement-visibility.ts:95`, `wiki-visibility.ts:102` (space/page/revision), `document-visibility.ts:91`, `quick-link-visibility.ts:83`. admin_role/editor behalten Draft-Zugriff (sie bypassen vorher und arbeiten im Admin-Panel). `publicationState` (v4-Schreibweise) ist in v5 zwar wirkungslos (kein Vorkommen in core/utils/database 5.49), wird aber mangels `api.rest.strictParams` NICHT gestrippt → wird ebenfalls gelöscht. Getestet in `policy-query.test.ts` + `announcement-visibility.test.ts`. **Neue Read-Policy auf einem draftAndPublish-Type ⇒ `forcePublishedStatus(query)` nicht vergessen.**
25. **Vollständigkeit von Listen, aus denen Sicherheits-/Report-Mengen berechnet werden:** Strapi liefert ohne `pagination[pageSize]` nur `api.rest.defaultLimit` = **25** Zeilen (@strapi/core `core-api/service/pagination.js:9`, hier nicht überschrieben). `api.teams.list()` hatte kein pageSize — der Ack-Report baute daraus user→teams und bekam ab Team #26 eine LEERE Zielmenge, die als grünes „alle bestätigt" gerendert wurde. Regel: Wer eine Liste zur *Berechnung* (nicht bloß zur Anzeige) braucht, nimmt einen Seiten-Walk mit harter Obergrenze (`lib/acknowledgements.ts`, `lib/users.ts`, `lib/teams.ts`, `api.events.rsvps`) UND meldet Unvollständigkeit nach oben (`fetchAllTeams` → `{teams, truncated}`). Und: eine nicht bestimmbare Zielmenge wird als **unbekannt** ausgewiesen, nie als „0 von 0 = alles erledigt" (`manage/acknowledgements/page.tsx`, i18n `ackReport.audienceUnknown`).

26. **Fan-out-Dedup je (Quelle, EMPFÄNGER)** (`apps/cms/src/utils/notification-source.ts`, Issue #12): Publish ist in Strapi 5 delete+recreate — jedes erneute Veröffentlichen einer Ankündigung/eines Events feuerte `afterCreate` wieder und benachrichtigte die komplette Zielgruppe erneut. Jede Fan-out-Notification trägt jetzt `sourceType` + `sourceDocumentId` (documentId, **nie** die Row-id — die wechselt beim Publish, §5.17). `resolveFanout()` lädt mit EINER Query (`findMany({where: sourceFilter(anchor), populate: {recipient: {select:["id"]}}})`) die bereits benachrichtigten Empfänger, `planFanout()` zieht diese Menge von der Zielgruppe ab — benachrichtigt wird nur die Differenz. **Granularität ist der Empfänger, nicht die Quelle**, und genau daran hängen drei Eigenschaften: (a) **Retargeting funktioniert** — Publish an Abteilung A, Korrektur auf Abteilung B, erneutes Publish ⇒ B bekommt die Meldung, A nicht doppelt (quell-granular bekam B NIE etwas, Recovery nur per Hand in der DB); (b) ein **Abbruch mitten im Fan-out** (k von n Zeilen geschrieben) ist **selbstheilend** — der nächste Publish stellt genau die fehlenden n−k zu; deshalb braucht die Schreibschleife **keine Transaktions-Klammer**, ein Teilschreiben ist ein reparabler, kein korrupter Zustand; (c) die Dedup-Query läuft jetzt NACH dem Aufbau der Zielgruppe (sie braucht sie zum Diffen) — Kosten: ein `findMany` statt eines `count`, weiterhin genau eine Query. **Fail-open by design:** fehlender documentId, fehlgeschlagene/unbrauchbare Abfrage oder ein Zielgruppen-Mitglied ohne brauchbare id ⇒ benachrichtigen (mit `strapi.log.warn`) statt schweigen. Bei Teil- oder Voll-Dedup ein `strapi.log.info` „`n of m recipient(s) already notified, k new`" — auch bei k=0, sonst sieht ein deduptes Re-Publish im Log wie ein stiller Fehler aus. Entscheidungslogik ist rein und getestet (`notification-source.test.ts`, 23 Tests: Retargeting, Teil-Fan-out-Heilung, ankerlose Altzeilen, leere Zielgruppe, alle Fail-open-Pfade), die Lifecycles sind nur der dünne Wrapper (Muster wie `announcement-audience.ts`). Der zweite Pfad (`afterUpdate`) bleibt bewusst stehen: er fängt Publishes ab, die `publishedAt` in-place setzen (DB-Layer-Update aus Skripten/Imports), und kann dank Dedup nicht mehr doppelt feuern. **Bekannte Grenze (akzeptiert):** check-then-insert ohne DB-Unique — `recipient` ist eine Link-Table-Relation, dieselbe Constraint wie bei ack/rsvp/poll-vote (§7b, [#16](https://github.com/yurtbayemre/sinnlos/issues/16)); zwei echt parallele Publishes können beide schreiben. Duplikate sind damit ein Foto-Finish-Artefakt, kein systematisches Re-Notify mehr.

27. **documentId-Anker für comment/reaction + Bootstrap-Backfill** (`apps/cms/src/utils/comment-target.ts`, Web-Spiegel `apps/web/src/lib/comment-target.ts`, Issue #11): Beide Ziel-Typen (announcement, wiki-page) sind draftAndPublish, Publish = delete+recreate ⇒ die `targetId`-Row-id wechselte bei jedem Veröffentlichen und ALLE Kommentare/Reaktionen verwaisten. Anker ist jetzt `targetType` + `targetDocumentId`; `targetId` bleibt deprecated in der Tabelle (Migrations-Brücke + Rollback-Anker). **Temporäre Schreib-Brücke, beide Zweige in `resolveWriteTarget` (comment- UND reaction-Controller):** (a) **Dual-Write** — jede neue Zeile bekommt den Anker UND die aktuelle Row-id des Ziels (published bevorzugt, exakt was `findCommentTarget` auflöst), sonst wären nach einem VOLLSTÄNDIGEN Rollback auf den id-only-Code alle zwischenzeitlich geschriebenen Zeilen unsichtbar (der alte Code filtert nur über `targetId`). Doppelte Treffer sind ausgeschlossen, weil der Legacy-Lesezweig durch `targetDocumentId IS NULL` geklammert ist — eine dual-geschriebene Zeile matcht ausschliesslich über den Anker-Zweig (Test: `targetMatchWhere` gegen echte Zeilen, CMS + Web). (b) **Write-Bridge** — fehlt `targetDocumentId`, ist aber ein gültiges `targetId` dabei (ALTER web-Container gegen NEUES CMS, also genau der Teil-Rollback aus `infra/deploy.sh`), wird das Ziel per Row-id aufgelöst und dessen documentId als Anker geschrieben, statt jeden Kommentar/jede Reaktion mit 400 abzulehnen; eine mitgeschickte Draft-Row-id wird dabei auf die published Row-id kanonisiert. 400 nur noch bei unbekanntem `targetType`, bei komplett fehlendem Ziel-Key oder wenn das Ziel gar nicht auflösbar ist (letztere beiden mit IDENTISCHER Meldung — kein Existenz-Orakel für documentIds, §5.17-Muster; nebenbei entstehen so keine verwaisten Zeilen mehr für Fantasie-documentIds). Ein vom Client geschicktes `targetId` wird nie roh gespeichert und kann den Anker nicht umbiegen: liegt ein `targetDocumentId` an, gewinnt es. **Beide Zweige fallen mit der Spalte** (Folge-Ticket zu #11, s. §7). **Backfill im Bootstrap** (`index.ts` `backfillTargetAnchors`, direkt nach `seedAdminUser`, also VOR dem ersten Request): läuft nur über Zeilen mit `targetDocumentId IS NULL`, ist damit nach dem ersten Lauf ein No-Op (Muster REVOKED_PERMISSIONS), cached die Ziel-documentIds pro (uid, Row-id), läuft als Seiten-Walk (500er-Batches, Offset = Zahl der bewusst übersprungenen Zeilen) und **rät nie**: fehlt das Ziel oder ist targetType/targetId unbrauchbar, bleibt die Zeile unverändert und wird in EINER `strapi.log.warn`-Zeile mit Anzahl + Beispiel-ids gemeldet; ein Fehler bricht den Boot nicht ab (Log + nächster Start macht weiter). Verifiziert gegen eine SQLite-Kopie des Datenmodells: 5 comment- + 7 reaction-Zeilen migriert (inkl. wiki-page-Zweig), 2 unauflösbare korrekt übersprungen, zweiter Start ohne Aktion. **Temporärer Lese-Fallback** (`targetMatchWhere` CMS / `targetFilterQuery` Web): der Legacy-Zweig matcht `targetId` NUR zusammen mit `targetDocumentId IS NULL` — ohne diese Klammer würde eine bereits verankerte Zeile eines FREMDEN Eintrags mitkommen, sobald ein Re-Publish deren alte Row-id an einen anderen Datensatz vergibt. Zusätzlich prüft der Web-Layer jede geladene Zeile nochmal (`matchesTarget`, auch in `summarize(reactions, userId, target)`). **qs-Falle:** Strapis Query-Parser hat Tiefe 5 — `filters[$or][1][$and][0][targetDocumentId][$null]` ist eine Ebene zu tief, qs liefert dann den Literal-Key `[$null]` und `validateQuery` antwortet 400 (an @strapi/utils 5.49 reproduziert). Die beiden Legacy-Bedingungen stehen deshalb als implizites AND im SELBEN `$or`-Element. Der reaction-Controller benutzt die aus `resolveWriteTarget` ohnehin bekannte Row-id des Ziels für den Toggle mit, damit eine noch unverankerte eigene Reaktion abschaltbar bleibt statt eine zweite Zeile zu erzeugen. Entfällt komplett mit der `targetId`-Spalte.

**P1.4 — ~~`/uploads/*` ohne Authentifizierung~~ BEHOBEN** ([#21](https://github.com/yurtbayemre/sinnlos/issues/21))**:** Strapi lieferte die Dateibytes ohne Session (das `GET /uploads/(.*)` des Upload-Plugins läuft mit `auth: false`; verifiziert 2026-08-16: PDF → 200 ohne Cookie, während `/api/documents` 403 gibt). **Entscheidung (Architecture Record): Option 2 — Session-Gate auf die Datei-Bytes, am ORIGINAL-Pfad.** Beide Edge-Configs routen `/uploads` nicht mehr zu Strapi (Traefik-Labels + Caddyfile; Achtung Raw-Prefix-Landmine, s. §1), es fällt in den Web-Catch-all: `proxy.ts` redirectet Anonyme zu `/sign-in` (`/uploads` steht bewusst NICHT in der Public-Allowlist), und die neue Route `apps/web/src/app/uploads/[...path]/route.ts` prüft die Auth.js-Session selbst nochmal (401-Fallback, falls der Matcher je verengt wird), validiert jedes Pfadsegment strikt (`^[A-Za-z0-9][A-Za-z0-9._-]*$` — kein Traversal Richtung cms) und streamt die Bytes intern via `STRAPI_URL` durch (Range/If-None-Match/If-Modified-Since und 200/206/304/404 werden durchgereicht; `Cache-Control: private, max-age=3600`; 30s-Timeout NUR bis zu den Response-Headern — der Body streamt danach ohne Deadline (große Downloads dürfen dauern, aber ein Slowloris-Aufbau hängt nicht ewig; Review-Fund N1); upstream `Accept-Encoding: identity`, sonst zerlegt undicis Auto-Dekompression den Content-Length). Original-Pfad heißt: alle gespeicherten Media-URLs (`mediaUrl()`, alte Links, Admin-Thumbnails) bleiben ohne Migration gültig. **Bewusst KEINE Abteilungs-Sichtbarkeit auf Datei-Ebene** — Restrisiko: ein EINGELOGGTER Mitarbeiter kann bei bekannter Hash-URL Bytes fremder Abteilungs-Dokumente laden (vorher konnte das JEDER anonym); dafür wirkt Offboarding jetzt sofort (Session weg = Datei-Zugriff weg). **Betriebshinweis:** Die Strapi-Admin-Mediathek lädt Thumbnails als plain `<img>` von `/uploads/…` und die Admin-Auth ist Bearer-only (serverseitig nie als Cookie ausgewertet) — Admins brauchen daher eine PARALLELE Intranet-Session im selben Browser, sonst bleiben die Thumbnails leer (alle Admins sind Mitarbeiter, akzeptiert; die `/upload`-JSON-XHRs der Mediathek laufen mit Bearer und sind unberührt). **KRITISCH — Traversal-Seitenkanal + cms-Token-Riegel (Review-Fund K1):** Das Edge-Rerouting allein genügt NICHT. Weil `PathPrefix` ein ROHER String-Präfix ist, routet `/api/../uploads/<hash>.pdf` (und die Encodings `/api/%2e%2e/uploads/…`, `/api/..%2fuploads/…`) über den `/api`-Router AN cms vorbei am Web-Gate — und cms serviert die Bytes trotzdem: die koa-static-Route von `strapi::public` (`/((?!uploads/).+)`) matcht den noch un-normalisierten Pfad und koa-send löst das `..` zurück in `public/uploads` auf (live gegen Prod bewiesen 2026-08-17: %PDF anonym). Riegel dagegen ist routing-UNABHÄNGIG: die globale cms-Middleware `apps/cms/src/middlewares/uploads-auth.ts` (registriert VOR `strapi::public` in `config/middlewares.ts`) verlangt bei jedem Request, dessen DEKODIERTER+NORMALISIERTER Pfad unter `/uploads/` auflöst, den Shared-Header `x-internal-upload-token` (timing-safe verglichen, `INTERNAL_UPLOAD_TOKEN` aus `infra/.env` an cms UND web durchgereicht) — sonst blankes 404. NUR die Proxy-Route sendet den Token; damit ist `/uploads` von cms von außen nur noch intern über web erreichbar. In Prod fail-closed (ohne Token → 404), im Dev/Standalone No-Op (kein Traefik-Traversal-Surface). Der Paritätstest pinnt den Leak (`TRAVERSAL_TO_CMS` in `infra/routing-parity.test.ts`), damit niemand das Edge-Routing für den Schutz hält.

**P1.5 — ~~Login ohne Rate-Limit~~ BEHOBEN** ([#23](https://github.com/yurtbayemre/sinnlos/issues/23))**:** Der Passwort-Login lief als Server Action über den `sinnlos-web`-Catch-all (kein Ratelimit), und `POST /api/auth/callback/local` ruft `authorize()` DIREKT auf (CSRF-Token von `/api/auth/csrf` holbar, scriptbar) — ein Limit nur am Pfad/Router wäre also umgehbar. Autoritativ sitzt der Limiter deshalb IN `authorize()` (`apps/web/src/auth.ts` → `lib/login-rate-limit.ts`): Sliding-Window in-memory (EIN Node-Prozess im standalone-Container; die Instanz ist auf `globalThis` gepinnt, weil Turbopack das Modul in mehrere Layer-Chunks mit getrennten Modul-Registries kompiliert — Server-Action-Layer vs. `/api/auth`-Route-Layer — und ein Modul-Scope-Singleton im Prod-Build MEHRFACH mit getrennten Buckets existierte; Reset bei Container-Neustart akzeptiert), zwei Dimensionen, es zählen NUR echte Verifikationsfehler (Strapi antwortet auf falsche Credentials mit 400; 5xx/429/Netzwerkfehler zählen NICHT, sonst sperrte ein Strapi-/DB-Ausfall legitime Retry-Nutzer bis 15min nach Recovery — und eine Büro-NAT mit vielen legitimen Logins drosselt nie) — pro Client-IP 10/60s, pro Identifier (case-insensitiv normalisiert) 10/15min über ALLE IPs; Erfolg resettet nur den Identifier-Bucket. Geloggt wird `[login-rate-limit]` (volle IP + maskierter Identifier) NUR beim Übergang in den Block-Zustand — einmal pro Sperr-Fenster, nicht pro abgewiesenem Folgeversuch, sonst wären über den Callback ~100 Log-Zeilen/s scriptbar. Speicher gedeckelt: Prune beim Zugriff + hartes 10.000-Key-Cap je Dimension mit Eviction des ältesten NICHT aktiv gesperrten Buckets (die ersten 100 werden geprüft; sind alle geblockt, fällt trotzdem der älteste — harte Obergrenze gewinnt) — sonst wäre der Limiter selbst per Zufalls-Identifier ein Memory-DoS. Client-IP = erster `x-forwarded-for`-Eintrag (vertrauenswürdig: Traefik/Caddy überschreiben gespoofte Werte), Fallback `x-real-ip`, dann `"unknown"` (lokaler Dev); IPv6 wird auf das /64-Präfix gekeyed (ein Anschluss = EIN Bucket statt 2^64 rotierbarer Adressen; IPv4-mapped-Adressen keyen als IPv4). Login- UND Register-Call an Strapi schicken die echte Client-IP als `X-Forwarded-For` mit — Strapis eigener users-permissions-Throttle (10/60s pro `ctx.ip`, cms hat `proxy:true`) zählte sonst alle Nutzer im EINEN Bucket der Web-Container-IP (10 fremde Fehlversuche/min sperrten ALLE aus). Der Register-Pfad hängt am SELBEN Limiter (isBlocked-Gate vor dem Strapi-Call, Fehlversuche mit Status <500/≠429 zählen) und hat `AbortSignal.timeout(5000)` in try/catch bekommen (Timeout/Netzwerkfehler → `{error}`-State statt Digest-Fehlerseite). Am Edge zusätzlich Router `sinnlos-signin` (POST auf `/sign-in`|`/register`, prio 90) mit neuer Middleware `sinnlos-authlimit` (10/s, burst 20 — zählt auch ERFOLGREICHE Logins, daher NAT-freundlich dimensioniert; nur Grobnetz, autoritativ bleibt der App-Limiter, der nur Fehlversuche zählt) (`infra/docker-compose.traefik.yml`; bestehende Middleware-Namen unangetastet — cms referenziert sie cross-container). Die Server Action zeigt per read-only Peek (zählt nicht als Versuch) eine ehrliche „Too many failed attempts“-Meldung statt „Invalid email or password“. Getestet in `login-rate-limit.test.ts` (Fenster/Sliding, IP- vs. Identifier-Dimension, Lockout über mehrere IPs, Erfolg-Reset, Case-Normalisierung, IPv6-/64-Keying, Cap/Eviction inkl. Schutz aktiver Sperren, Übergangs-Semantik des Logs, XFF-Parsing). Bewusste Grenzen: **Konto-Lockout-DoS AKZEPTIERT** — ein Angreifer mit bekannter E-Mail kann ein Konto mit ~1 Req/90s dauerhaft gesperrt halten (10 Fehlversuche/15min); vor dem Fix konnte er über Strapis Shared-Bucket ALLE Konten sperren, jetzt nur noch einzelne gezielt; Gegenmittel (CAPTCHA/progressive Delays) bewusst nicht gebaut. Eine Identifier-Flood kann per Eviction angefangene Zähler unterhalb der Sperre auswaschen (AKTIVE Sperren überleben sie, den Speicher sprengt sie nie, und aus einer Quelle trippt sie vorher die IP-Dimension). Strapis „Email is already taken“-Antwort im Register-Pfad bleibt ein vorbestehendes E-Mail-Enumerations-Orakel (akzeptiert: Registrierung in Prod deaktiviert, `REGISTRATION_ENABLED`). Im Caddy-Profil gibt es kein Edge-Pendant (Caddy ohne Plugin ohne Ratelimit) — der App-Limiter greift dort genauso, die #22-Drift-Liste wächst dadurch nicht (neuer Router ist Traefik-only als bewusstes Extra, keine Routing-Semantik).

- **~~Re-Notify-Duplikate bei Re-Publish~~ BEHOBEN** ([#12](https://github.com/yurtbayemre/sinnlos/issues/12))**:** publish = delete+recreate → JEDES Re-Publish feuerte den afterCreate-Fan-out erneut. Jetzt trägt jede Fan-out-Notification den Quell-Anker `sourceType` + `sourceDocumentId` (§5.26); `resolveFanout()` lädt die zu diesem Anker bereits benachrichtigten Empfänger (eine Query) und benachrichtigt nur die Zielgruppen-Mitglieder, die dort NICHT stehen — protokolliert als „n of m recipient(s) already notified, k new". `afterUpdate` bleibt als Safety-Net stehen (kann durch den Dedup nicht mehr doppeln), die OPEN-ISSUE-Kommentare sind ersetzt. **Dedup je EMPFÄNGER, nicht je Quelle:** eine nachträglich geänderte/erweiterte Zielgruppe wird beim nächsten Publish sehr wohl nachbenachrichtigt (die früher hier dokumentierte Grenze gilt NICHT mehr), und ein abgebrochener Fan-out heilt sich beim nächsten Publish selbst — deshalb ohne Transaktions-Klammer. Es bleibt der check-then-insert-Race aus §7b/[#16](https://github.com/yurtbayemre/sinnlos/issues/16) (kein DB-Unique möglich, `recipient` ist Link-Table-Relation): nur zwei echt parallele Publishes können doppeln. **Bestandsdaten bewusst NICHT gebackfillt:** die 106 Altzeilen haben keinen Anker, ihr einziger Bezug zur Quelle ist der Titel im Notification-Text — der ist weder eindeutig (24 Titel, keine Unique-Constraint) noch stabil (Umbenennen + neue Meldung mit dem alten Titel würde die Altzeilen an das falsche Dokument hängen und dort eine echte Benachrichtigung dauerhaft unterdrücken). Folge, akzeptiert und dokumentiert: das ERSTE Re-Publish einer alten Ankündigung/eines alten Events benachrichtigt einmalig erneut, danach nie wieder — ein einmaliges Duplikat gegen stillen Nachrichtenverlust getauscht. **Offen (kein Bug):** Der `link` einer Notification ist heute eine statische Listen-URL (`/announcements`, `/events`, `/kudos`) und enthält gar keine Row-id — die Deep-Link-Landmine aus #11 trifft Notifications also nicht. Mit dem neuen Anker wäre ein Deep-Link auf die Quelle möglich, es fehlen aber die Zielrouten (kein `/announcements/[id]`, unter `/events/[id]` liegt nur die ICS-Route) bzw. ein Fokus-Parameter in den Listenseiten — das ist ein Web-Umbau, nicht Teil von #12.
- **~~comment/reaction hängen am Row-id-Anker~~ BEHOBEN** ([#11](https://github.com/yurtbayemre/sinnlos/issues/11))**:** beim Re-Publish eines Announcements wechselte dessen numerische id → Kommentare/Reaktionen wären verwaist.
