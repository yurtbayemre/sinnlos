## 1. Überblick & Topologie

Sinnlos ist ein Firmen-Intranet als pnpm-Monorepo mit zwei Apps (dazu das Regel-Paket `packages/domain` = `@sinnlos/domain`, §5.91): `apps/web` (Next.js 16, fast rein serverseitig, App Router + RSC) und `apps/cms` (Strapi 5, Node 24, Postgres in Prod / SQLite standalone). Das Web-Frontend ist ein dünner, session-behafteter Layer vor Strapi: alle Pages sind async Server Components, die über einen zentralen `strapi()`-Fetch-Client (`apps/web/src/lib/strapi/client.ts`, Fassade `lib/strapi.ts`, Reads in `lib/api/*.ts`, Seitendaten seit Batch 14 aus `lib/loaders/*.ts`) mit dem Strapi-JWT der Auth.js-Session lesen; Mutationen laufen ausschließlich über Server Actions in `apps/web/src/lib/*-actions.ts`. Autorisierung liegt konzeptionell im CMS (Rollen-Bootstrap + Route-Policies); das Web-Layer prüft Rollen nur für UI-Gates (`isAdmin`). Auth: lokale Credentials und optional Microsoft Entra ID (seit Batch 9, nur mit `ENTRA_ENABLED=1`, Default aus: Auth.js-OIDC gegen genau einen Tenant, dann ein server-seitiger POST-Exchange `/api/auth/entra/exchange`, in dem das cms das ID-Token selbst prüft und den Strapi-JWT ausstellt; §3 Punkt 2, §5.68), beides env-geschaltet; ein `DEMO_MODE=1` ersetzt Strapi komplett durch In-Memory-Fixtures (`lib/demo.ts`).

Deployment: 4-Container-Stack via `docker compose -p infra` (`infra/docker-compose.yml`): `db` (postgres:16-alpine) → `cms` (Strapi :1337) → `web` (Next standalone :3000) → optional `caddy`. In Prod (VPS, `sinnlos.yurtbay.dev`) deaktiviert `infra/docker-compose.traefik.yml` den Caddy (`profiles: [manual]`) und hängt web+cms per Labels an den Host-Traefik (externes Netz `frontend`, TLS via `lehttp`; seit 2026-09-29 nimmt jede Router-Regel den Host aus `DOMAIN` in `infra/.env`, Pflicht, §5.71). Intern sprechen sich die Container seit 2026-09-29 über die Aliase `sinnlos-db`, `sinnlos-cms`, `sinnlos-web` an, die nur im Projektnetz existieren (§5.73). Das Pfad-Routing ist die zentrale Topologie-Invariante — **Router-Prioritäten: `/api/auth/*` → web (Prio 100), POST `/sign-in`|`/register` → web (Prio 90), `/api|/admin|/upload|…` → cms (Prio 50), `/live/*` → web ohne Kompression (Prio 10, seit 2026-09-29), Catch-all → web (Prio 1)** — und existiert doppelt (Traefik-Labels + `infra/Caddyfile`); die Doppelpflege ist seit [#22](https://github.com/yurtbayemre/sinnlos/issues/22) durch `infra/routing-parity.test.ts` abgesichert (Prefix-Mengen + Verhaltens-Proben unter den ECHTEN Matcher-Semantiken beider Proxies). **`/uploads` (Datei-Bytes) geht seit [#21](https://github.com/yurtbayemre/sinnlos/issues/21) bewusst NICHT mehr zu Strapi**, sondern an den Web-Catch-all → session-gegatete Proxy-Route `apps/web/src/app/uploads/[...path]/route.ts` (s. §7b P1.4). **Matcher-Landmine dabei:** Traefiks `PathPrefix` matcht als ROHER String-Präfix (an Traefik 3.7 live verifiziert: `/email` matcht `/emailXYZ`) — `PathPrefix(\`/upload\`)` würde `/uploads` weiter schlucken, daher steht die Media-Library-Admin-API segment-exakt als ``Path(`/upload`) || PathPrefix(`/upload/`)`` in den Labels (Caddy-Pendant: `/upload /upload/*`). Konsequenzen im Code: Next-eigene Endpunkte dürfen nicht unter `/api/*` liegen (ICS-Route lebt unter `/events/[id]/ics`), `/admin` ist für Strapi reserviert, und der einzige session-lose Next-Endpunkt `/api/live/emit` (Live-Event-Ingest, §6) ist von außen unerreichbar, weil Traefik `/api` zu Strapi routet — CMS ruft ihn intern über `WEB_INTERNAL_URL` auf (der frühere Revalidate-Webhook `/api/revalidate` ist seit 2026-09-24 entfernt, D-DC01). **Case-Landmine (D-EDGE-01, 2026-09-24):** Traefiks ``PathPrefix(`/api/auth`)`` ist case-sensitiv, Strapis Koa-Router nicht (`sensitive: false`) — `/api/Auth/local` fiel am Web-Router vorbei an den cms-Router und erreichte Strapis lokalen Login (und register/forgot/reset/change-password) ohne den Web-Login-Limiter. Der Riegel ist cms-seitig und routing-unabhängig: die globale Middleware `global::auth-path-guard` (`apps/cms/src/middlewares/auth-path-guard.ts`, eingetragen in `config/middlewares.ts`) beantwortet jede Schreibweise außer dem wörtlichen kleingeschriebenen `/api/auth/…` (Case-Varianten, `%`-kodiert, `//`, `..`; folgt `api.rest.prefix`) mit blankem 404. Caddy matcht ohnehin case-insensitiv. Alle legitimen Aufrufer (Web-Server, `live-smoke.sh`) rufen cms intern mit dem wörtlichen Pfad.

```
Browser ──HTTPS──> Traefik (frontend-Netz; Host = DOMAIN)
                     ├─ /api/auth/* ────────────> web:3000  (Auth.js)
                     ├─ /api|/admin|/upload|… ──> cms:1337  (Strapi; NICHT /uploads; eigene Middlewares)
                     ├─ /live/* ────────────────> web:3000  (SSE, ohne Kompression)
                     └─ /* (inkl. /uploads) ────> web:3000  (Next RSC; /uploads = Session-Gate-Proxy)
web ──Bearer strapiJwt (server-seitig aus dem verschlüsselten Session-Cookie)──> cms ──> db (postgres, kein Host-Port)
web ──GET /uploads/* (intern, STRAPI_URL=http://sinnlos-cms:1337, x-internal-upload-token)──> cms (Datei-Bytes für die Session-Route)
cms ──POST /api/live/emit (x-revalidate-secret)──> web (intern, WEB_INTERNAL_URL=http://sinnlos-web:3000; Live-Pings, §6)
```

## 3. Request-/Datenfluss

**Auth-Kette:**
1. Route-Guard: `apps/web/src/proxy.ts` (Next-16-„proxy", Nachfolger von middleware.ts) prüft pro Request die Auth.js-Session (`auth()` — neben `auth.ts` die EINZIGE Stelle, die `auth()` direkt ruft; seit 2026-09-29c erst NACH der Public-Allowlist, öffentliche Pfade kosten keinen Session-Decode, §5.79), redirectet unauth → `/sign-in?from=…` (mit `expired=1`, wenn noch ein Session-Cookie mitkam; eine Server Action bekommt statt 307 die `x-action-redirect`-Antwort, §5.79). Public-Allowlist = exportierte, getestete Funktion `isPublicPath()` (`proxy.ts`, `proxy.test.ts`): `/sign-in`, `/register`, `/api/auth` (roher Präfix), **`/api/live/emit` (exakt — der EINZIGE session-lose interne Endpunkt; `/api/revalidate` ist seit D-DC01 weg und fällt unter den Guard)**, `/_next`, `/favicon` + exakte PUBLIC_FILES. `/uploads` und `/live/*` stehen bewusst NIE drin. Das `?from=`-Ziel läuft durch `safeInternalPath()` (`lib/utils.ts`): seit FX10 werden Steuerzeichen, DEL und Backslash abgelehnt und der Wert mit dem WHATWG-Parser gegen einen Platzhalter-Origin aufgelöst — `/<TAB>/evil.example` war vorher ein Open Redirect (Browser strippen TAB/LF erst NACH der Präfix-Prüfung). `DEMO_MODE=1` schaltet alles ab (Prod-Guard in `auth.ts` wirft dann beim Start).
2. Login Microsoft (seit Batch 9 Lane 4A, D-ENTRA-01, nur mit `ENTRA_ENABLED=1`; Details §5.68): Auth.js führt den OIDC-Code-Flow gegen genau einen Tenant (Issuer aus der Tenant-GUID, Scope `openid profile email User.Read` ohne `offline_access`, `profile()` nur aus den Claims). Der `signIn`-Callback prüft `tid`, POSTet ID-Token und Graph-Access-Token an `${STRAPI_URL}/api/auth/entra/exchange` (Header `x-entra-exchange-secret`, 10 s, ein Retry nach 500 ms nur bei Netzfehler/502/503/504; `lib/entra-exchange.ts`) und reicht die Antwort per WeakMap unter dem `account`-Objekt an den jwt-Callback; eine Ablehnung wird zum Redirect `/sign-in?error=entra_<code>`. Das cms prüft das ID-Token selbst (jose, Tenant-JWKS, iss/aud/tid, iat ≤ 10 min plus 5 min Clock-Toleranz, effektiv ≤ 15 min), liest Graph `/me` (optional `checkMemberGroups`, `/me/manager`) parallel mit 3 s Timeout, findet den User per (tid, oid), legt neue User sofort an (unabhängig von `LOCAL_REGISTRATION`), schreibt Rolle, Profil, Abteilung und Manager und stellt einen Strapi-JWT für `ENTRA_SESSION_TTL` (Default 12 h) aus; die Web-Session endet mit ihm. **Entfernt:** der GET-Exchange `/api/auth/microsoft/callback?access_token=` (von users-permissions 5.51+ ohnehin mit 400 „OAuth authentication requires a completed provider session“ abgelehnt, das war seit Batch 2 der Zustand), die auf 5.49 inerte damalige Extension `extensions/users-permissions/strapi-server.ts` (sie wies `callback` der Controller-Factory zu; seit FX40 liegt unter diesem Pfad die Token-Version-Erweiterung, §5.104), `config/ms-role-map.ts` (Rollen nach Gruppen-displayName) und der nie gelesene `providers`-Block in `plugins.ts`; Strapis eigener Microsoft-Provider wird bei jedem Boot abgeschaltet (§5.69). Instanzen, die noch den alten Flow auf dem 5.49-Image fahren, wechseln direkt auf die neue Anmeldung (DEPLOYMENT.md „Upgrading to the Entra sign-in (batch 9, lane 4A)“).
3. Login lokal: Credentials-Provider → Strapi `/api/auth/local` mit der echten Client-IP als `X-Forwarded-For` (Strapis Throttle zählt seit FX11 pro Client-IP, §5.1); ein Strapi-429 wird als `StrapiRateLimitedSignIn` (`lib/auth-errors.ts`, Code `rate_limited`) zur eigenen Meldung `auth.rateLimited` statt „Invalid email or password" (change-password analog `profile.passwordRateLimited`). Danach `/api/users/me` NUR für id + Anzeigename — **Rolle und Abteilung werden beim Login NICHT mehr geladen**: users-permissions strippt `role` aus `/users/me` für jeden ohne `role.find`, also für alle außer admin_role (bei guest auch `department`) — die alte Session hatte deshalb für jeden lokalen Nicht-Admin und jeden Microsoft-User `role = undefined`.
4. Session (D-SESSION-01, §5.33): JWT-Strategie. Die Session (= was `GET /api/auth/session` an den Browser liefert) trägt NUR `user` {id, name, email, image}, `provider` und `expires`. Der Strapi-JWT (+ `strapiJwtExp`) lebt NUR im verschlüsselten Auth.js-JWT (HttpOnly-Cookie) und wird server-seitig von `lib/strapi-token.ts` per `getToken()` entschlüsselt — Zugriff ausschließlich über `getStrapiToken()` (`lib/session.ts`, prüft zuerst `getSession()`). Die Session **endet mit dem eingebetteten Strapi-JWT**: der jwt-Callback gibt ab `strapiJwtExp` (bei Alt-Tokens aus dem JWT dekodiert) oder ohne JWT `null` zurück → Auth.js löscht das Cookie, `auth()` liefert null (`lib/strapi-jwt.ts`). `maxAge` 7d (= Strapi-`expiresIn`, `config/plugins.ts`) ist nur noch Obergrenze — das Cookie selbst gleitet bei jedem Session-Read, die alte Annahme „maxAge exakt = Strapi-JWT-TTL, non-sliding" stimmte so nicht. Der Cookie-Name folgt dem AUTH_URL-Schema (https → `__Secure-authjs.session-token`); `strapi-token.ts` spiegelt die Auth.js-Regel und MUSS jeden künftigen `useSecureCookies`/`cookies`-Override in `auth.ts` mitziehen (gepinnt in `auth.test.ts`).
5. Jeder Server-Fetch: `strapi()` holt den Bearer über `getStrapiToken()`; Autorisierung entscheidet Strapi (Matrix grob, Route-Policies + globale Guards fein, §5.8). 401 mit Token → `redirect("/sign-in?expired=1")` (die Sign-in-Seite bounct dann eine noch vorhandene Session nicht zurück); jedes andere Nicht-2xx wirft `StrapiError` mit `.status` (`lib/strapi-error.ts`, Meldungstext unverändert).
6. **Viewer (D-SESSION-01):** `getViewer()` (`lib/viewer.ts`) liest Rolle + Abteilung pro Request aus `GET /api/me` (FX02-Allowlist, für jede Rolle gegrantet) — einmal pro RSC-Render (React `cache()`), in Server Actions und Route Handlern bei jedem Aufruf. 401 → Expired-Redirect (NEXT_REDIRECT wird durchgereicht), jeder andere Fehler → `role: null` (alle Gates verweigern, `[viewer]`-Log). Rollenänderungen im Strapi-Admin wirken damit beim nächsten Request, ohne Re-Login. Kosten: ein `/api/me`-GET pro Render bzw. pro gatender Action (Sidebar rendert auf jeder Seite). DEMO_MODE liefert einen festen Demo-Viewer (member).

**Caching — seit 2026-09-24 KEINES (D-DC01, Kopfkommentar von `lib/strapi/client.ts`):**
- Vertrag: Das Web hält KEINE server-seitige Kopie von Strapi-Antworten zwischen Requests — kein Next-Fetch-/Data-Cache-Eintrag, kein `unstable_cache`, kein `'use cache'`, kein In-Process-Memo von Response-Bodies. Jeder Strapi-Request geht mit `cache: "no-store"`; `StrapiInit` (= `RequestInit` ohne `cache`/`next`) lehnt die Cache-Knöpfe zur Compile-Zeit ab, `strapi()` strippt sie zusätzlich zur Laufzeit. Entfernt sind die `noCache`-Option, die Tags, `utils/revalidate.ts` samt den revalidate-only-Lifecycles und `POST /api/revalidate` → `revalidateTag`.
- Warum: Die alte Begründung „der Next-Fetch-Cache keyed nur per URL und ignoriert den Authorization-Header" war FALSCH — Next 16.3.4 hasht URL, Methode und ALLE Request-Header inkl. Authorization in den Key. Die getaggten Reads waren also ein Eintrag pro JWT: kein Cross-User-Leak, aber auch fast keine Wiederverwendung, dafür unbegrenztes Plattenwachstum (`.next/cache/fetch-cache`), Stale-Reads (auch für gesperrte User und abgelaufene JWTs) und eine Webhook-Pipeline, deren Tags großteils keinen Konsumenten hatten.
- Wiederverwendung NUR innerhalb eines Requests: identische GETs in einem RSC-Render dedupliziert Nexts Fetch-Dedupe; `getSession()` (`lib/session.ts`, `cache(async () => DEMO_MODE ? DEMO_SESSION : auth())`, §5.79) dekodiert die Session einmal pro Render, `getViewer()` liest `/api/me` einmal pro Render. Server Actions und Route Handler bekommen keines davon.
- Frische: ein committeter Strapi-Write (Admin-Panel, REST, Seed) erscheint beim nächsten Server-Render (Navigation, Reload, `refresh()` in einer Action, `router.refresh()`) — ohne Webhook. Ist Strapi down, zeigen Listen das `FetchErrorBanner`, nie eine alte Liste. Preis: ca. 1–3 zusätzliche interne GETs pro Dashboard-/Listen-Ansicht.
- Guardrails: `StrapiInit`-Typ + Laufzeit-Strip; ESLint-Regeln in `apps/web/eslint.config.mjs` verbieten `next/cache`-APIs außer `refresh`, `next: { revalidate | tags }`, `cache`-Modi außer `no-store`/`no-cache`, Segment-`fetchCache` außer den `*-no-store`-Werten (`"force-cache"` würde `no-store` in Nexts gepatchtem fetch übersteuern und pro JWT unbegrenzt cachen) und `'use cache'`; `strapi.test.ts` pinnt den Vertrag.
- **Re-Entry-Regel:** Ein server-seitiger Cache darf nur zurückkommen, wenn ALLES gilt: (i) gemessener Bedarf an EINEM konkreten Read, (ii) Payload für jede berechtigte Rolle identisch, (iii) Abruf mit eigenem read-only Strapi-API-Token (nur `find` auf diesen Types), (iv) ein Web-Check, der den Strapi-Grant spiegelt, läuft vor der Auslieferung (guest ausgeschlossen, sofern nicht gegrantet), (v) Invalidierung nach Commit, (vi) gebaut mit `'use cache'` + `cacheTag` nach Aktivieren von `cacheComponents`. Per-User- oder policy-gefilterte Strapi-Antworten server-seitig zu cachen ist ausgeschlossen — das braucht eine neue Entscheidung.
- Mutierende Server Actions: `refresh()` aus `next/cache`. Kommentare/Notifications: primär SSE-Pings (§6 „Live-Updates"), Polling nur noch als Backstop — gesund 60s/120s, degradiert die alten 10s/30s, nur bei sichtbarem Tab; die Kommentar-Sektionen einer Seite seit 2026-09-28l mit EINEM Intervall und gebündelten Refetches (§5.67).
- Paginierte Sammel-Fetches laufen als bounded Page-Walk (`pageSize` 100 als Client-Wahl; das cms setzt kein `api.rest.maxLimit`, `lib/paginate.ts`): eigene Acks max 20 Seiten (`/announcements` und `/documents`). Der Ack-Report walkt seit v0.31 nicht mehr: 20 Einträge je Abschnitt und Seite, ihre Bestätigungen mit einem `POST /api/acknowledgements/report-index` je Abschnitt; das Dashboard-Banner zählt per `GET /api/me/open-acks` (§5.52). RSVPs werden seit 2026-09-28e nicht mehr gewalkt: das cms aggregiert sie (`GET /api/event-rsvps/summary`, `lib/api/events.ts` `rsvpSummaries` (Fassade `api.events.rsvpSummaries`), §5.51; vorher bis 30 Seiten Roh-Rows).

**Fehler-Strategie:** Listen-Seiten nutzen `tryFetch()` (`lib/safe-fetch.ts`, rethrowt NEXT_REDIRECT via `unstable_rethrow`) → Inline-`FetchErrorBanner`; Detail-Seiten mit `notFound()`-Semantik lassen Fetch-Fehler bewusst zur `(app)/error.tsx` propagieren — seit 2026-09-28b alle sechs einheitlich, mit id-Prüfung vor dem Read und Metadaten, die nie scheitern (§5.41). Client-Mutationen fangen abgelehnte Actions selbst ab (Inline-Fehler, §5.44).

**P1.5 — ~~Login ohne Rate-Limit~~ BEHOBEN** ([#23](https://github.com/yurtbayemre/sinnlos/issues/23))**:** Der Passwort-Login lief als Server Action über den `sinnlos-web`-Catch-all (kein Ratelimit), und `POST /api/auth/callback/local` ruft `authorize()` DIREKT auf (CSRF-Token von `/api/auth/csrf` holbar, scriptbar) — ein Limit nur am Pfad/Router wäre also umgehbar. Autoritativ sitzt der Limiter deshalb IN `authorize()` (`apps/web/src/auth.ts` → `lib/login-rate-limit.ts`): Sliding-Window in-memory (EIN Node-Prozess im standalone-Container; die Instanz ist auf `globalThis` gepinnt, weil Turbopack das Modul in mehrere Layer-Chunks mit getrennten Modul-Registries kompiliert — Server-Action-Layer vs. `/api/auth`-Route-Layer — und ein Modul-Scope-Singleton im Prod-Build MEHRFACH mit getrennten Buckets existierte; Reset bei Container-Neustart akzeptiert), zwei Dimensionen, es zählen NUR echte Verifikationsfehler (Strapi antwortet auf falsche Credentials mit 400; 5xx/429/Netzwerkfehler zählen NICHT, sonst sperrte ein Strapi-/DB-Ausfall legitime Retry-Nutzer bis 15min nach Recovery — und eine Büro-NAT mit vielen legitimen Logins drosselt nie) — pro Client-IP 10/60s, pro Identifier (case-insensitiv normalisiert) 10/15min über ALLE IPs; Erfolg resettet nur den Identifier-Bucket. Geloggt wird `[login-rate-limit]` (volle IP + maskierter Identifier) NUR beim Übergang in den Block-Zustand — einmal pro Sperr-Fenster, nicht pro abgewiesenem Folgeversuch, sonst wären über den Callback ~100 Log-Zeilen/s scriptbar. Speicher gedeckelt: Prune beim Zugriff + hartes 10.000-Key-Cap je Dimension mit Eviction des ältesten NICHT aktiv gesperrten Buckets (die ersten 100 werden geprüft; sind alle geblockt, fällt trotzdem der älteste — harte Obergrenze gewinnt) — sonst wäre der Limiter selbst per Zufalls-Identifier ein Memory-DoS. Client-IP = erster `x-forwarded-for`-Eintrag (vertrauenswürdig: Traefik/Caddy überschreiben gespoofte Werte), Fallback `x-real-ip`, dann `"unknown"` (lokaler Dev); IPv6 wird auf das /64-Präfix gekeyed (ein Anschluss = EIN Bucket statt 2^64 rotierbarer Adressen; IPv4-mapped-Adressen keyen als IPv4). Login- UND Register-Call an Strapi schicken die echte Client-IP als `X-Forwarded-For` mit — Strapis eigener users-permissions-Throttle (10/60s pro `ctx.ip`) zählte sonst alle Nutzer im EINEN Bucket der Web-Container-IP (10 fremde Fehlversuche/min sperrten ALLE aus). **Korrektur 2026-09-24 (FX11):** das damalige `proxy: true` war die v4-Schreibweise und wurde von Strapi 5 still ignoriert — der Bucket blieb bis FX11 gepoolt; erst `proxy: { koa: true }` macht die weitergereichte IP wirksam (§5.1). Am Edge zusätzlich Router `sinnlos-signin` (POST auf `/sign-in`|`/register`, prio 90) mit neuer Middleware `sinnlos-authlimit` (10/s, burst 20 — zählt auch ERFOLGREICHE Logins, daher NAT-freundlich dimensioniert; nur Grobnetz, autoritativ bleibt der App-Limiter, der nur Fehlversuche zählt) (`infra/docker-compose.traefik.yml`; bestehende Middleware-Namen unangetastet — cms referenziert sie cross-container). Getestet in `login-rate-limit.test.ts` (Fenster/Sliding, IP- vs. Identifier-Dimension, Lockout über mehrere IPs, Erfolg-Reset, Case-Normalisierung, IPv6-/64-Keying, Cap/Eviction inkl. Schutz aktiver Sperren, Übergangs-Semantik des Logs, XFF-Parsing). Bewusste Grenzen: **Konto-Lockout-DoS AKZEPTIERT** — ein Angreifer mit bekannter E-Mail kann ein Konto mit ~1 Req/90s dauerhaft gesperrt halten (10 Fehlversuche/15min); vor dem Fix konnte er über Strapis Shared-Bucket ALLE Konten sperren, jetzt nur noch einzelne gezielt; Gegenmittel (CAPTCHA/progressive Delays) bewusst nicht gebaut. Die Suite pinnt die Invarianten (kein 5xx, bei RSVPs jede 200 = eine Row, bei Votes am Ende genau eine Row und eine gezählte Stimme, sonst die erwartete 400, danach hält das Gate), nicht die Anzahl. **Poll-Votes seit der Batch-8-Integration entschärft** (§5.39): `results` zählt je Voter nur die erste Stimme (kleinste id, `utils/poll-ballots.ts`), und jeder Vote löscht nach seinem Insert die späteren Rows desselben Voters für den Poll, sodass die gespeicherten Daten auf genau diese Stimme konvergieren. Duplikate aus der Zeit davor zählen ab dem Deploy nur noch einmal — die Summen betroffener Polls sinken auf eine Stimme je Voter; die Abfrage dafür steht in DEPLOYMENT „Deploying batch 8“.
