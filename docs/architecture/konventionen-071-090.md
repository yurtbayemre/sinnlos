71. **Edge je Instanz: Traefik-Host aus `DOMAIN`, Caddy mit Header-Parität (Traefik-Host-Parametrisierung, FX33, QW-FX33; 2026-09-29, `infra/docker-compose.traefik.yml`, `infra/Caddyfile`, `infra/docker-compose.yml`):**
    - **Traefik:** alle fünf Router-Regeln matchen ``Host(`${DOMAIN:?…}`)`` statt des Owner-Hostnamens; dieselbe Overlay-Datei bedient jede Instanz (Arbeitgeber-Instanz), aber nur ein Sinnlos-Stack je Traefik: Router-, Service- und Middleware-Namen sind fest (`sinnlos-*`), eine zweite Instanz (Arbeitgeber, Staging) braucht einen eigenen Host bzw. Traefik. Hinter dem Produktions-Traefik löschte sie dessen Router (anderes `DOMAIN`: gleichnamige Router mit abweichender Konfiguration verwirft Traefik alle, beide Seiten antworten 404) oder teilte seine Services (gleiches `DOMAIN`: gleichnamige Services vereinen ihre Server, Produktionsanfragen landen auch auf den Containern und der Datenbank der anderen Instanz), beides ohne Fehler beim Deploy. Pflicht, bewusst OHNE Default: ein Default würde eine Instanz ohne `DOMAIN` still auf einem fremden Host lauschen lassen. Ohne `DOMAIN` rendert compose den Overlay nicht (`required variable DOMAIN is missing a value`), damit bricht `infra/deploy.sh` im Preflight (`compose config -q`) vor Backup und Tagging ab. Wert = nackter Hostname ohne Schema und Port = Host von `WEB_PUBLIC_URL`. Seit der Batch-10-Integration prüft der Preflight von `infra/deploy.sh` (auch `--check`) den Wert an den gerenderten Labels (`traefik_host_scan`: der Host aus jeder `traefik.http.routers.*.rule`): alle Router EIN Host, nackter Hostname (kein Schema, Port, Pfad oder Leerzeichen), kein Platzhalter (`example.com`/`.net`/`.org` samt Subdomains, die TLDs `.example` und `.invalid`, `change-me`, `your-domain`) und gleich dem Host von `WEB_PUBLIC_URL` (web `AUTH_URL`) und `CMS_PUBLIC_URL` (cms `PUBLIC_URL`), weil der Overlay beide Apps auf diesem einen Host bedient; sonst `ERROR: DOMAIN in infra/.env does not fit this instance:` mit den Hosts (keine Secrets) und Abbruch vor Backup und Container-Wechsel. Die Smoke-URL ist seitdem `https://$DOMAIN` (der geprüfte Host; `SMOKE_URL` überschreibt, `--check` druckt beide) statt des Owner-Hosts, und `infra/live-smoke.sh` nimmt ohne `BASE_URL` `https://$DOMAIN`, `DOMAIN` aus der Umgebung oder dem `infra/.env` neben dem Skript (Tests `deploy-preflight.test.ts`, `deploy-flow.test.ts`, `live-smoke.test.ts`). `routing-parity.test.ts` rendert die Labels wie compose (`interpolateCompose`: `${VAR}`, `:-`, `-`, `:?`, `?`, `$$`; jedes andere `$` wirft) mit `DOMAIN=intranet.example.com`; gepinnt: jeder `Host()` ist ein Pflicht-`${DOMAIN:?…}`, rendert mit jedem Wert, verweigert ohne oder mit leerem `DOMAIN`. Der CI-Job `infra` prüft dasselbe am echten `docker compose config` (jq).
    - **Caddy:** compose übergibt `DOMAIN: ${DOMAIN:-localhost}` (vorher gar nicht: eine Standalone-Installation lieferte immer `localhost`). Echter Hostname → Let's Encrypt und 80→443; ungesetzt/`localhost` → HTTPS mit Zertifikat der internen Caddy-CA (kein Let's Encrypt; Vertrauen nur per Import der Root auf dem Host, `caddy trust` im Container wirkt nur dort); `http://localhost` → Klartext. Header-Block wie die Traefik-Middlewares: `nosniff`, `Referrer-Policy`, `X-Frame-Options: DENY`, dieselbe `Permissions-Policy`, `-Server`, `defer` (Werte ERSETZEN die des Upstreams — `strapi::security`/helmet setzt auf cms-Antworten `SAMEORIGIN`, `no-referrer` und eigenes HSTS; ein nicht-deferred Set gäbe doppelte Header). HSTS nur `@hsts { protocol https; not host localhost }`; `@localhost { host localhost }` entfernt zusätzlich Strapis eigenes HSTS (sonst pinnte `/admin` auf einem localhost-Caddy den Browser ein Jahr lang auf HTTPS für jeden lokalen Port). caddy-Service: `no-new-privileges`, 256 MB, 1 CPU, 128 pids. Keine Edge-Rate-Limits in Caddy (unverändert).
    - **Modell:** der Caddy-Parser kennt Matcher-Blöcke (`protocol`, `host`, `not host`), bedingte und deferred Header-Blöcke und bedingte Removals (fail-closed für alles andere, eigene Tests); `caddyResponseHeaders` rechnet die Header auf einer Upstream-Antwort (leer und Strapis helmet-Satz) je Protokoll und Host. `KNOWN_CADDY_HEADER_GAPS` ist weg: beide Proxys senden dieselben Namen und Werte.
    - **Probelauf** (compose-caddy-Service eines Wegwerf-Projekts): mit Nicht-localhost-`DOMAIN` genau ein HSTS, `DENY` und die Policy auf `/` und `/admin`; auf `localhost` kein HSTS, auch nicht Strapis; `/live/stream` unkomprimiert (Caddys `encode` respektiert `no-transform`).

72. **Traefik-Middlewares je Container, Live-Router ohne Kompression (FX34; 2026-09-29, `infra/docker-compose.traefik.yml`):**
    - **Kopplung aufgelöst:** Traefiks Docker-Provider verwirft ALLE Labels eines Containers, solange er startet, ungesund oder gestoppt ist, und bedient keinen Router, dessen Middleware fehlt. `sinnlos-cms` nutzte die am web definierten `sinnlos-headers/-ratelimit/-compress` → `/admin` und `/api` antworteten bei jedem Web-Neustart mit 404 (im Probelauf mit dem Batch-9-Overlay reproduziert). Jetzt definieren die cms-Labels `sinnlos-cms-headers`, `sinnlos-cms-ratelimit` und `sinnlos-cms-compress` mit den Werten des Webs; mit gestopptem Web antworten `/admin` 200, `/api/events` 403 (anonym) bzw. 200 (mit JWT). Parity-Test: jeder Router referenziert nur Middlewares SEINES Containers, keine Middleware bleibt unbenutzt, cms-Kopien = Web-Optionen und -Header; die FX34-Charakterisierung ist umgedreht.
    - **Abweichungen vom Plan (Owner-Default „repo-only“):** Kompression bleibt am cms-Router — Strapi komprimiert selbst nicht (kein `strapi::compression` in `config/middlewares.ts`), das Admin-Bundle ginge mit 5,5 MB statt 1,9 MB (gzip) raus. Kein `sinnlos-cms-authlimit`: kein cms-Router braucht ihn (die Admin-Anmeldung drosselt Strapi selbst, `admin::rateLimit`), eine unbenutzte Middleware wäre toter Code.
    - **Live-Router:** `sinnlos-live` = `Host && PathPrefix(/live/)`, Prio 10 (über dem Catch-all, unter cms), nur `sinnlos-headers`, kein Rate-Limit (wie bisher im Catch-all). Traefik v3.7.13 gzippt `text/event-stream` hinter `compress` trotz `Cache-Control: no-transform` (Wegwerf-Traefik mit SSE-Upstream, 2026-09-29); der Stream floss nur, weil Traefik flusht. `compress.excludedContentTypes` prüft den RESPONSE-Typ und verhindert es — beide compress-Middlewares schließen `text/event-stream` zusätzlich aus (für jede künftige SSE-Route). Probelauf: `/live/stream` mit Session und `curl --compressed` ohne `content-encoding`, `infra/live-smoke.sh` grün; alle anderen 15 geprüften Pfade mit identischen Security-Headern wie vorher.

    - **`runCmsAction(fn, { label, mapError, after, data })`:** zuerst `unstable_rethrow` (der 401-Redirect von `strapi()` wird nie ein Ergebnis), dann die aktionseigene `mapError` (Status, `error.name`, `error.message`, `error.details`), dann die gemeinsame Abbildung: 400 → `invalid` (+ `fields` aus `details.keys`/`details.codes`, ein Key ohne Code → `invalid`), 401 (nur ohne Token erreichbar) und 403 → `forbidden`, 404 → `notFound`, 412 → `conflict` (+ `version` = `details.current`), 428 → `failed` (Fehler-Log), 429, 5xx und Netzwerkfehler (TypeError, Timeout, Abort) → `unavailable`, sonst `failed`. Log: eine Ablehnung (4xx) als `console.warn` `<label> refused: <status> <name> → <code>`, Ausfall, Bug und 428 als `console.error` mit Fehler. `after` (etwa `refresh()`) läuft nur nach Erfolg. `parseStrapiError`/`StrapiError` tragen jetzt auch `details` (`strapiDetails`).
    - **Umgestellt:** `acknowledgeAnnouncement`, `sendKudos`, `addComment`, `deleteComment`, `toggleReaction`, `markNotificationsRead`, `markAllNotificationsRead`, `votePoll`, `rsvpToEvent`, `completeLesson`; `createPoll` angeglichen (`CreatePollResult = ActionResult<"missingQuestion" | "tooFewOptions">`, das Formular hat `polls.formError_<code>` für jeden Code); ist der Viewer nicht lesbar (`/api/me` gescheitert, `getViewer()` liefert `ANONYMOUS_VIEWER` ohne id), antwortet es `unavailable` statt `forbidden` (Fix-Runde; vorher las ein Editor im cms-Ausfall „Nur Admins und Editoren können Umfragen erstellen.“), ohne Anfrage. Ungültige Argumente (keine documentId, eine Poll-Referenz oder ein Optionstext außerhalb der Regeln, eine Kommentar-id, die keine positive Ganzzahl ist — sie landet nie im Pfad) antworten `invalid` vor jeder Anfrage, statt zu werfen.
    - **Spezifische Codes:** RSVP `full` (400 + exakte Meldung „Event is at capacity“; ersetzt den Substring-Check auf dem rohen Fehlertext), Vote `pollOptionsChanged` (400 „Poll options changed“, die Batch-9-Karte mit veralteten Optionen: eigener Text statt „vielleicht schon abgestimmt“, die Karte lädt neu). Ein nacktes `ctx.badRequest()` trägt keinen Maschinencode (jede 400 dort heißt `BadRequestError`), deshalb der exakte Vergleich der geparsten Envelope-Meldung; beide Texte sind per Test gegen die cms-Controller gepinnt (`event-actions.test.ts`, `poll-actions.test.ts`). Seit der Batch-12-Integration ebenso Kommentar und Reaktion: die 400 „targetDocumentId required“ (`WRITE_TARGET_ERRORS["unresolved-target"]`: Ziel unbekannt, für den Aufrufer unsichtbar, eine depublizierte oder abgelaufene Ankündigung, §5.86 — byte-gleich, kein Existenz-Orakel) ist `notFound` („Dieses Element gibt es nicht mehr — Seite neu laden“) statt `invalid` mit der Wiederholen-Aufforderung; das Web sendet immer einen Anker, die Meldung heißt hier also nur „Ziel weg“ (`comment-actions-writes.test.ts` pinnt den Text gegen `utils/comment-target.ts` und beide Controller). Seit der zweiten Fix-Runde ebenso die Lesebestätigung: „Target not available for acknowledgement“ (unbekannt, depubliziert, nicht pflichtig, außerhalb der Zielgruppe, abgelaufen) ist `notFound`, „Already acknowledged“ bleibt `invalid` (`acknowledgement-actions.test.ts` pinnt den Text gegen den Controller). Offen: Maschinencodes (`details.codes`, Muster Entscheidung 06 §B5) im cms für diese Ablehnungen.
    - **Client:** `startCmsAction(startTransition, { optimistic, action, onSuccess, onFailure, onSettled })` wendet das optimistische Update zuerst an, reicht den Code an die Komponente, meldet einen abgelehnten Aufruf (Web-Server nicht erreichbar, von Next maskierter Fehler) oder ein scheiterndes `onSuccess` als `unavailable` und wirft den Sign-in-Redirect weiter. `forbidden`, `notFound`, `conflict` und `unavailable` haben EINEN gemeinsamen Text (`actionErrors.*`, `isSharedErrorCode`), `invalid` und `failed` den eigenen der Aktion („Kommentar konnte nicht gesendet werden“). 89. **Auth-Module und reservierender Login-Limiter (WD09, FX39; `lib/auth/credentials.ts`, `lib/auth/callbacks.ts`, `lib/login-rate-limit.ts`):**
    - `authorizeCredentials(input, { strapiUrl, fetch, limiter, now, warn })` ist der reine Kern von `authorize()`: Zählregel unverändert (400 und andere 4xx zählen; 5xx, 429 und Netzwerkfehler nicht; 429 wirft `StrapiRateLimitedSignIn`, FX11; ein vom Limiter abgewiesener Versuch wirft `LoginBlockedSignIn` mit demselben Code `rate_limited`, die Action antwortet `rateLimited` statt `invalidCredentials`, Fix-Runde), die E-Mail aus der `/auth/local`-Antwort, Name und id aus `/users/me` — neu: scheitert dieser Lesezugriff, steht der User der `/auth/local`-Antwort ein (vorher scheiterte ein korrekter Login). `createAuthCallbacks({ entra, strapiUrl, exchange })` hält signIn (Tenant-Prüfung, Exchange, `entra_*`-Redirects, Batch 9), die WeakMap-Übergabe an `jwt` und das Session-Ende mit dem Strapi-JWT (Batch 10) unverändert; `auth.ts` verdrahtet beides und re-exportiert `callbacks`/`ENTRA_PROVIDER_ID`. `auth-actions.ts` nutzt `unstable_rethrow` statt Digest-String-Prüfungen.
    - **FX39:** `tryAcquire(ip, identifier)` prüft UND reserviert in einem synchronen Schritt je einen Platz im IP- und im Identifier-Bucket (Ticket oder `"blocked"`), `settle(ticket, "success" | "failure" | "neutral")` macht daraus einen Fehlversuch oder gibt den Platz zurück (Erfolg leert weiterhin den Identifier-Bucket). Vorher prüften parallele Versuche alle `isBlocked`, bevor der erste Fehler gezählt war — ein Burst ging am Limit vorbei. Jetzt halten laufende Versuche ihren Platz (höchstens 10 pro IP bzw. Identifier gleichzeitig unterwegs; ein Login dauert unter einer Sekunde, Timeout 5 s), gezählt bleiben nur Verifikationsfehler. `settle` meldet den Übergang in die Sperre genau einmal (der Log `[login-rate-limit] block engaged` bleibt einmal pro Sperrfenster), ist idempotent und ignoriert fremde Tickets; ein Fehler, dessen Bucket ein paralleler Erfolg geleert hat, zählt neu. `globalThis`-Pin, Eviction-Regeln und `isBlocked` (der read-only Peek der Sign-in-Action) unverändert. Die Register-Action nutzt denselben Ablauf; ein angelegtes Konto settelt `neutral` (es beweist kein Passwort eines bestehenden Kontos und setzt nichts zurück, der Login danach settelt selbst).
